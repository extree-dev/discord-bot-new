# Changelog

Формат по [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/), версии — по [Semantic Versioning](https://semver.org/lang/ru/).

Текущую версию показывает команда `/version`, она же логируется при старте бота и берётся из `package.json`.

PATCH-версия (`X.Y.Z`, `Z > 0`) — багфикс, MINOR/MAJOR (`X.Y.0`) — релиз. В канал `#обновления` автоматически публикуются только релизы; патчи остаются только здесь и в `/changelog`.

**Правило бампа версии** (до 3.9.0 не соблюдалось — каждый PR, включая чистые багфиксы, ошибочно бампил MINOR, из-за чего в `#обновления` уходило вообще всё):

- Багфикс, мелкая правка, новая точка настройки к уже существующей фиче (админ-команда, скрипт) — PATCH (`X.Y.Z+1`). Не анонсируется, но версия и `CHANGELOG.md` обновляются сразу вместе с самим PR.
- Новая фича, которую стоит анонсировать участникам — копится в `## [Unreleased]` без бампа версии и без правки `package.json`. Версия бампается в MINOR (`X.(Y+1).0`) отдельным, осознанным шагом "релиза" — по явному запросу, а не автоматически при каждом мерже.

## [Unreleased]

### Добавлено

- **Испытательный срок для staff тикетов** — новые роли `Beta-Moderator`/`Beta-Support` (`scripts/setup-roles.js`/`scripts/setup-tickets.js`): видят и ведут тикеты как обычный staff, но закрыть тикет сразу не могут — запрос на закрытие карточкой с кнопками "Подтвердить"/"Отклонить" уходит в новый канал `#подтверждение-стажёров`, который видит только старший состав (Support, Moderator, Admin). Подтверждение закрывает тикет как обычно (в лог добавляется отдельная строка "Подтвердил"), отклонение просит указать причину модалкой и возвращает тикет в работу с уведомлением в треде. На автора тикета, закрывающего свой же тикет, гейт не распространяется, даже если он сам на испытательном сроке.
- **Баг-репорты — отдельная система от тикетов поддержки.** Тема "Баг / техническая проблема" (`REASONS[].standalone: true`) больше не на общей панели тикетов (апелляции/жалобы/общие вопросы/другое) — своя панель в новом канале `#сообщить-о-баге`, свой тред при открытии, пингуется только роль «Разработчик бота» (Support больше не дёргается на баг-репорты). Движок общий с тикетами — claim/close/заметки/шаблоны/`/ticket stats` работают как обычно, просто с другим "входом". Роль «Разработчик бота» (раньше — чисто пинг-уведомление) теперь и полноправный staff для тикетов этой темы: сама берёт в работу и закрывает баг-репорт, без Support/Moderator — обобщённый механизм (`isStaff()` теперь принимает тикет и проверяет специалист-роль именно его темы), так что то же самое автоматически работает и для специалистов по жалобам/апелляциям на их тикетах.
- **Доработка тикетов и баг-репортов** (общий движок, применяется к обеим системам):
    - **Отпустить / переназначить** — кнопки «Отпустить» и «Переназначить» появляются рядом с «Взять в работу», как только тикет взят в работу; доступны тому, кто ведёт тикет, или старшему составу (не любому staff — иначе кто угодно мог бы снять чужой тикет с исполнителя без его ведома). Переназначение — через UserSelectMenu, с проверкой, что выбранный участник вообще staff для этого тикета.
    - **HTML-транскрипт вместо `.txt`** — лог переписки при закрытии тикета теперь красиво оформленная HTML-страница (тёмная тема, аватарки, вложения ссылками), открывается прямо в браузере вместо плоского текстового файла. Весь пользовательский контент (ник, текст сообщений, имена вложений) экранируется, чтобы чужой ввод не мог превратиться в исполняемую разметку внутри файла, который открывает staff.
    - **Приоритет вручную** — новая кнопка «Приоритет» в самом тикете: переключить может как staff, так и автор тикета (не только staff — по просьбе администратора: автору лучше знать, насколько срочно ему нужна помощь), не только у тем, заранее отмеченных как urgent. Виден отдельной строкой в карточке тикета (не эмодзи-маркером в имени треда — по фидбэку администратора эмодзи-маркеры в именах тредов вообще убрали, включая и статус-кружки), карточка перерисовывается сразу при переключении. Приоритетные тикеты идут первыми в `/ticket list` и эскалируются быстрее (используется уже существовавшая логика `entry.urgent`/`urgentClaimTimeoutMs`).
    - **Быстрый ответ кнопкой** — кнопка «Быстрый ответ» прямо в тикете открывает тот же список готовых шаблонов, что и `/ticket reply`, без набора команды.
    - **Среднее время первого ответа** — `/ticket stats` теперь показывает, сколько в среднем проходит времени между открытием тикета и первым ответом staff (`firstStaffReplyAt`), в дополнение к количеству закрытых и средней оценке.
- **DM-уведомление о наказании + апелляция прямо из личных сообщений.** `/ban`, `/timeout` и кнопка «Наказать» в тикетах-жалобах теперь присылают наказанному участнику личное сообщение с типом наказания и причиной (раньше так делал только `/warn` — после бана/мута участник просто "замолкал" без объяснений). К DM о таймауте (не о бане — после бана участник уже не на сервере) добавлена кнопка «Подать апелляцию»: это единственный способ обжаловать наказание для участника в таймауте, потому что, пока таймаут действует, Discord не даёт нажать вообще никакую кнопку и использовать никакую слэш-команду на самом сервере (ограничение платформы, не бота) — а DM-взаимодействия с ботом этим не ограничены. Новый `utils/punishmentNotice.js` собирает уведомление, `tickets/handlers.js handleAppealDmButton` открывает по кнопке модалку темы "Обжалование наказания" прямо из личных сообщений (гильдия и участник резолвятся заново, раз `interaction.guild` в DM всегда `null`).

### Изменено

- **Ответы на команды и кнопки — ephemeral по умолчанию.** Единственное осознанное исключение — `/rep leaderboard` (топ должен быть виден всем в канале). Раньше большая часть команд уже была ephemeral, но не всё: `/rep give` и `/rep profile` отвечали публично, а часть ответов на кнопки в тикетах (взял в работу, подтверждение закрытия стажёра, "спасибо за оценку") были видны всему треду. Для случаев, где кнопка изначально жила на публичной персистентной карточке (запрос на подтверждение закрытия в `#подтверждение-стажёров`, карточка с оценкой после закрытия тикета) — саму карточку теперь правит обычный `Message#edit` (не interaction-ответ), а персональный результат уходит нажавшему отдельным ephemeral-сообщением, чтобы карточка оставалась полезной всем, но ответ — только автору действия. Добавлен `toEphemeralMessage()` в `utils/components.js` — та же сборка Components V2, что и `toMessage()`, но с флагом `Ephemeral`.
- `/rep profile` — теперь целиком одна картинка (не embed/текст): баннер профиля пользователя как фон (градиент в цвет уровня, если баннера нет), круглый аватар в рамке цвета уровня, имя, уровень, полоса прогресса того же цвета до следующего уровня, строка "осталось N очков"/сколько репутации сам выдал, место в рейтинге (золото/серебро/бронза для топ-3) и уголок с иконкой/именем сервера. Рисуется на сервере через `@napi-rs/canvas`. Цвет уровня теперь общий для роли и карточки — единственный источник в `reputation/model.js` `LEVELS`, вместо отдельного списка цветов в `scripts/setup-reputation.js`.
- `/rep leaderboard` и еженедельный автопост топа в `#рейтинг` — тоже картинкой вместо Components V2-сообщения со списком строк, тем же визуальным языком, что и `/rep profile`: все места — одинаковые строки (аватар в рамке цвета уровня, уровень с цветным индикатором, сколько репутации сам выдал, полоса прогресса до следующего уровня тем же цветом, счёт), топ-3 отмечены только цветом номера места. Первая версия делала топ-3 подиумом со звездой и свечением — по фидбэку оказалось слишком "игровым" по стилю, переделано на спокойный единый со всей системой репутации вид. У автопоста везде ещё и цветная плашка изменения позиции (`+N`/`-N`/`=`/`новый`). Общие примитивы рисования (шрифты, скруглённые прямоугольники, круглые изображения) вынесены из `rankCardImage.js` в `reputation/canvasUtils.js`, чтобы обе картинки репутации не дублировали одну и ту же логику.

## [3.9.8] — Beta-Support/Beta-Moderator теперь тоже пингуются и могут мутить через тикет

### Исправлено

- **Новый тикет пинговал только роль Support** — испытательный staff (`Beta-Support`/`Beta-Moderator`, см. 3.9-серию про испытательный срок) полноправно ведёт тикеты, но узнавал о новых обращениях только случайно, не по пингу. Теперь `createTicket()` пингует Support, Beta-Support и Beta-Moderator вместе (для обычных тикетов; у standalone-тем вроде багов пинг по-прежнему только специалист-роли — Support туда намеренно не дёргается).
- **Кнопка «Наказать → Мут» в тикете была недоступна Support/Beta-Support.** Эти роли намеренно не держат опасных Discord-прав (`ModerateMembers`/`BanMembers`) — доступ к тикетам им даёт членство в роли, а не разрешения сервера (см. `scripts/setup-roles.js`, `scripts/setup-tickets.js`). Но кнопка "Наказать → Мут" проверяла личное право `ModerateMembers` нажавшего, из-за чего они видели кнопку, но всегда получали отказ — даже притом что мут нарушителя по итогам разобранной жалобы как раз их прямая задача. Теперь мут выполняет от своего имени бот (у него `ModerateMembers` есть всегда), доступ проверяется на уровне тикета (`isStaff`, как и раньше проверялось для показа самой кнопки). Бан по-прежнему требует личного `BanMembers` у нажавшего — это более серьёзное решение, специально оставленное только Moderator/Admin.

## [3.9.7] — жалоба на игрока больше не добавляет нарушителя в тред

### Исправлено

- **Тикет "Жалоба на игрока" случайно раскрывал жалобу тому, на кого жаловались.** Карточка тикета ментионила нарушителя (`<@reportedUserId>`) прямо в стартовом сообщении приватного треда — а Discord автоматически добавляет упомянутого пользователя в участники треда при отправке такого сообщения, даже если тред приватный. В итоге нарушитель сам оказывался в числе участников треда и видел жалобу на себя. Та же проблема была и в уведомлениях после наказания (`ticket_punish`) — они тоже ментионили нарушителя прямо в треде. Везде, где карточка/сообщения показывают нарушителя внутри самого треда, теперь используется `model.formatReportedUser()` — tag нарушителя (снимается один раз при создании тикета) без `<@id>`-упоминания; в приватном логе `#тикет-лог` (отдельный от треда канал) упоминание оставлено как есть — там оно безопасно и удобно для перехода в профиль.

## [3.9.6] — audit-roles.js точнее находит пустые Administrator-роли

### Исправлено

- `scripts/audit-roles.js` предупреждал о лишних ролях с `Administrator` только когда их больше двух — реальный кейс на сервере (роли "Administrator" и пустая "Admin" без единого участника) в этот порог не попал и остался незамеченным в разделе "Находки", хотя в общем списке ролей был виден. Добавлена отдельная проверка: любая роль с `Administrator` без единого участника — явный сигнал неиспользуемого дубликата, вне зависимости от общего количества admin-ролей.

## [3.9.5] — диагностический отчёт по ролям сервера

### Добавлено

- `scripts/audit-roles.js` — разовый диагностический скрипт: печатает все роли сервера с правами, позицией в иерархии и числом участников; находит задвоенные по имени роли, опасные права у `@everyone`, слишком много ролей с `Administrator`, роли выше бота в иерархии (бот не может ими управлять); отдельно считает и печатает предложенный порядок ролей по "опасности" набора прав. Только читает и печатает — ничего на сервере не меняет и не входит в автодеплой, запускается вручную. Написан по запросу администратора после находки задвоенной роли "Admin" (см. 3.9.4) — прежде чем что-то переставлять в живой иерархии ролей, сначала нужен честный отчёт о текущем состоянии.

## [3.9.4] — /backup restore больше не дублирует переименованные роли/каналы, понятнее подпись "выдал" на карточках репутации

### Исправлено

- **`/backup restore` создавал дубликат роли, если её переименовали после снятия бэкапа** — так на сервере рядом с переименованной администратором ролью появился дубликат "Admin". `security/backup.js` искал роли/категории/каналы только по имени против снимка без ID — тот же класс бага, что чинился для setup-скриптов и категории "📋 Информация"/"🚪 Верификация", просто не был применён здесь. Бэкапы теперь хранят ID каждой роли/категории/канала, восстановление ищет по ID в первую очередь (переименование не мешает найти тот же объект), на имя откатывается только для старых бэкапов без ID или если объект правда удалён. Общая find-or-create логика вынесена из `scripts/lib/idempotent.js` в `utils/idempotent.js`, чтобы её мог использовать не только `scripts/setup-*.js`, но и `security/backup.js`.
- Подпись "Выдал: N" на карточках `/rep profile` и `/rep leaderboard` была неоднозначной — непонятно, о какой репутации речь (полученной или отданной) и учитывает ли `/rep set`. Переименовано в "Дал репутации другим: N" / "Дал другим: N" — однозначно про то, скольким людям сам отправил через `/rep give` (`/rep set` на это число не влияет, это не "выдача", а прямая правка счёта модерацией).

## [3.9.3] — /rep profile падал с ошибкой у пользователей с баннером профиля

### Исправлено

- `reputation/model.js` запрашивал баннер профиля с `size: 600` — Discord CDN принимает только степени двойки (16..4096), и любое другое значение роняет `bannerURL()` `RangeError`-ом ещё до рендера карточки. У пользователей без баннера код никогда не доходил до этой строки с реальным URL (падало бы только когда `bannerURL()` возвращает непустую ссылку), поэтому баг не проявлялся в тестах — только вживую, как только `/rep profile` вызвали для пользователя с загруженным баннером. Заменено на `size: 1024`. Добавлен регрессионный тест, проверяющий, что и аватар, и баннер запрашиваются только валидными размерами CDN.

## [3.9.2] — деплои больше не гонятся друг с другом, /rep profile не падал у второго подряд пользователя

### Исправлено

- **Корень повторного дублирования после 3.9.1.** `deploy.yml` не имел `concurrency`-группы: два push в `main` подряд (например, слияние двух PR с разницей в пару минут) запускали два деплоя параллельно — оба одновременно гоняли `scripts/setup-*.js` против одной и той же гильдии. ID-идемпотентность из 3.9.1 не спасала от этой гонки: оба процесса читали "ID ещё не сохранён" до того, как первый успевал его записать, и оба создавали канал/роль. Теперь `concurrency: group: deploy-${{ github.ref }}` ставит второй деплой в очередь вместо параллельного запуска.
- `scripts/lib/idempotent.js` теперь не выбирает случайное совпадение по имени, если дубли уже случились: детерминированно берёт самый старый ресурс (по snowflake ID) и явно предупреждает в логе деплоя, какие ID лишние — чтобы их можно было спокойно удалить руками, без гадания, какой из дублей "настоящий".
- Ещё несколько мест всё ещё искали канал/категорию только по имени, без сохранённого ID (тот же класс бага, что чинился в 3.9.1, но пропущенный в первом проходе): категория "📋 Информация" в `setup-changelog.js`/`setup-rules.js`/`setup-reputation.js` (общая для трёх фич, но не сохранялась ни в одном конфиге), категория/роли верификации в `setup-verification.js` (канал `channelId` вообще не использовался при поиске, несмотря на то что сохранялся), каналы `setup-suggestions.js`, категория/роль поддержки/роли-специалисты/лог-канал в `setup-tickets.js`. `setup-temp-voice.js` держал собственную копию той же find-or-create логики — теперь использует общую `scripts/lib/idempotent.js`.
- `/rep profile` отвечал "Взаимодействие не удалось" у второго пользователя подряд: рендер карточки делает force-fetch пользователя и параллельно тянет аватар/баннер с CDN Discord перед тем, как ответить — суммарно не укладывался в 3-секундное окно ответа на interaction стабильно. Добавлен `deferReply()`/`editReply()`.

## [3.9.1] — setup-скрипты больше не пересоздают переименованные роли/каналы

### Исправлено

- `scripts/setup-roles.js` (Admin/Moderator/Trusted), `scripts/setup-reputation.js` (роли уровней и канал `#рейтинг`), `scripts/setup-changelog.js` (канал `#обновления`) и `scripts/setup-rules.js` (канал `#правила`) искали роль/канал только по имени, без памяти о сохранённом ID — так же, как чинилось для верификации (3.1.3, 3.2.0) и временных комнат (3.9.0). Если администратор переименовал что-то из этого вручную, следующий деплой не находил его по старому имени и создавал рядом дубликат с дефолтным именем (или переименовывал обратно — так было в `scripts/setup-tickets.js` для ролей-специалистов тикетов). Общая безопасная логика вынесена в `scripts/lib/idempotent.js` и используется во всех этих скриптах — вместо повторения одной и той же проверки в каждом файле руками.

## [3.9.0] — ручная настройка категории временных комнат

### Добавлено

## [3.1.2] — исправлена проверка "уже верифицирован"

### Исправлено

Если у участника не было ни одной из двух ролей (например, админ вручную снял "верифицирован", не выдав обратно "не верифицирован"), бот ошибочно считал его верифицированным и отказывался показывать капчу, оставляя без роли "верифицирован" вообще. Тот же баг был бы у любого, кто зашёл на сервер до включения верификации.

## [3.0.0] — тикеты на тредах и Components V2, новые системы

### Добавлено

- Anti-nuke: защита от вебхук-нюка — новый вебхук в канале проверяется через audit log, и если его создал не доверенный пользователь, вебхук удаляется автоматически (требует intent `GuildWebhooks`).

- Система тикетов поддержки переписана на приватные **треды** вместо отдельных каналов: панель с кнопкой на каждую тему обращения → модальная форма с описанием (для жалобы на игрока — выбор нарушителя через `UserSelectMenu`), приветственная подсказка и мини-чеклист для staff под тему сразу при создании, история жалоб на игрока за 30 дней в карточке тикета, кнопка "Наказать" (мут/бан) прямо из тикета с проверкой реальных прав исполнителя, ускоренная эскалация для темы "Безопасность аккаунта", DM-напоминание автору, если он сам долго не отвечает, антиспам-задержка перед повторным открытием тикета, 14 готовых ответов (`/ticket reply`), оценка поддержки после закрытия, `/ticket list|stats|reopen`, `/mytickets`.
- Панель поддержки, карточка тикета и все постоянные сообщения тикетов переведены на Discord **Components V2** (`Container`/`TextDisplay`/`Separator`) вместо embed'ов — без единого эмодзи, отдельная кнопка на каждую тему обращения, единый серый цвет всех кнопок.

- Система предложений (`suggestions/`) — кнопка "Предложить идею" → модалка → публикация предложения в канал для обсуждения.
- `/status` (`presence/`) — фиксированный текст активности бота с шаблонами `{members}`/`{uptime}` либо ротация из нескольких вариантов по таймеру.

- `/changelog` и автоматический анонс новой версии в канале `#обновления` при первом запуске бота на ней (`changelog/`, `scripts/setup-changelog.js`).

## [2.0.0] — инфраструктурный рефакторинг

### ⚠️ Важное изменение (breaking)

- Хранение конфигурации переведено с файлов `data/*.json` на **PostgreSQL**. Бот больше не запустится без рабочего `DATABASE_URL`. Для переноса существующих данных — `npm run db:migrate-json`.

### Добавлено

- `Dockerfile` и `docker-compose.yml` — контейнеризация бота вместе с PostgreSQL.
- eslint + prettier + CI на GitHub Actions (с сервисом PostgreSQL для тестов).
- Unit-тесты на встроенном `node:test` для чистой бизнес-логики.
- `README.md` с инструкциями по установке и настройке.
- `utils/pgStore.js` — атомарный read-modify-write через транзакцию с `SELECT ... FOR UPDATE` (защита от гонок даже при нескольких инстансах бота).
- Публичный API `security/index.js` (`getConfig`, `updateConfig`, `createBackup`, `listBackups`, `restoreBackup`, `VERIFY_BUTTON_ID`) — команды и скрипты настройки больше не обращаются к внутренним файлам `security/` напрямую.

### Изменено

- Устранена гонка read-modify-write в JSON-хранилище (была до перехода на PostgreSQL) — атомарная запись через отдельную очередь на файл.
- `tickets/tickets.js` и `voice/tempChannels.js` разделены на `model.js` (домен: правила, создание/закрытие тикета, действия над комнатой) и `handlers.js` (роутинг Discord-взаимодействий через карту `customId → функция` вместо цепочки `if/else`).
- `index.js`: graceful shutdown по `SIGINT`/`SIGTERM` (закрывает соединение с Discord и пул PostgreSQL).
